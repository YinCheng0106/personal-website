# DPIP｜第一次把 Flutter 跟 SwiftUI 結合，開發 iOS 天氣 Widget

**專案：** DPIP（ExpTechTW 團隊專案）\
**主要技術：** Flutter、Dart、Swift、SwiftUI、WidgetKit、App Group\
**個人參與：** iOS 天氣 Widget 功能提案、開發與相關改善

## 為什麼會想做 iOS 天氣 Widget？

其實一開始，DPIP 團隊並沒有特別規劃要開發 iOS 天氣 Widget。

這個功能是我自己提出來的。

因為 DPIP 本身是使用 Flutter 開發的，所以平常大部分功能都會直接在 Flutter 裡面完成，比較少需要碰到 iOS 原生的東西。

但我自己對 Apple 的原生開發蠻有興趣的，所以就開始想，既然 DPIP 已經有很多資訊，那有沒有可能把 Flutter 跟 Swift、SwiftUI 結合起來，做一些更符合 iOS 使用習慣的功能？

後來我去研究，發現 Flutter 確實可以透過原生橋接與 Swift 溝通，也能搭配 WidgetKit 開發 iOS 小工具。

既然可以做到，我就決定實際試試看。

### 為什麼先選擇天氣？

主要是因為我自己就有這個需求。

平常使用 iPhone 時，我有時候會覺得 Apple 內建天氣的預報跟實際狀況有落差，所以也會想參考中央氣象署的資訊。

當然，這只是我個人的使用經驗，並不是說 Apple 天氣一定比較不準。兩邊使用的資料來源和預報方式有所不同，實際準確度還是需要透過客觀比較才能判斷。

剛好 DPIP 本身就有天氣功能，也整合中央氣象署相關資料，那為什麼不把這些資訊直接放到 iPhone 主畫面上？

我覺得查看天氣其實是一件很簡單的事情。

有時候只是想知道現在幾度、會不會下雨，或是接下來幾個小時天氣會怎麼變化，不一定需要特別打開 App。

如果手機一打開就能直接看到這些資訊，對使用者來說應該會方便很多。

我當時就是希望，**讓使用者用越少的步驟，取得自己真正需要的資訊。**

如果 Widget 做得好用，也許還能讓更多人認識 DPIP，這當然也是我當初的一個期待。

## Flutter 的資料，要怎麼給 iOS Widget 使用？

真正開始實作後，首先要處理的就是 Flutter 與原生 iOS 之間的資料交換。

因為 Widget 不是 Flutter App 裡面的其中一個頁面，而是獨立的 iOS Extension。

這代表不能直接假設 Flutter App 現在記憶體裡面有什麼資料，Widget 就一定讀得到。

最後採用的方式，是透過 **App Group 共享天氣快照**。

大致的資料流程是：

1. Flutter 端取得並整理天氣資料。
2. 透過 Platform Channel 把需要的資料交給 iOS 原生程式。
3. Swift 將天氣快照寫入 App Group 的共享儲存空間。
4. Widget Extension 再從共享空間讀取資料，透過 WidgetKit 呈現。

這樣的好處是，即使使用者沒有開啟 DPIP，Widget 也能使用先前儲存的天氣資訊。

而且這不是把 Flutter 的畫面直接搬過去，而是讓 Flutter 負責原有的資料處理，再由 SwiftUI 建立原生 Widget 介面。

這也是我第一次比較完整地接觸 Flutter 與 Swift 之間的整合。

[相關實作：PR #576](https://github.com/ExpTechTW/DPIP/pull/576)

## 一個 Widget 不一定只要顯示目前所在地

在設計 Widget 時，我也希望使用者不一定只能查看目前所在地。

例如，有些人可能想同時知道自己住的地方跟學校的天氣，或者想另外查看家人的所在地。

如果每個 Widget 都只能顯示同一個地點，其實就少了很多彈性。

所以後來也加入了個別 Widget 的地點設定，讓使用者可以選擇目前所在地，或 DPIP 裡面已經儲存的地點。

這個功能除了 UI 設定之外，背後也需要處理資料的對應方式。

因為當使用者在主畫面放了好幾個 Widget，如果不同地點的天氣資料沒有分開管理，就可能發生顯示錯誤的情況。

因此，每個 Widget 都需要能夠根據自己的地點設定，讀取對應的天氣快照。

另外，也要考慮原本儲存的地點被刪除、設定失效，或是舊資料格式無法確認的情況，不能直接把不確定的資料當成正確地點顯示。

[相關實作：PR #579](https://github.com/ExpTechTW/DPIP/pull/579)

## Widget 不是想更新就能更新

整個開發過程其實大致上都蠻順利的。

如果真的要說比較需要花時間研究的地方，我覺得是 Widget 的更新機制，以及天氣資料本身的時間和格式。

一開始要先搞懂 WidgetKit 的生命週期。

它跟一般 App 不一樣，不是想什麼時候執行就能隨時執行。

WidgetKit 有自己的 Timeline 機制，系統會決定什麼時候重新載入 Widget，背景網路請求也會受到系統限制。

所以如果只是把天氣 API 串接好，然後顯示在 Widget 上，其實還不夠。

還需要考慮：

- 目前顯示的資料是什麼時候取得的？
- 如果 App 沒有開啟，Widget 要怎麼更新？
- API 暫時沒有回應時，應該怎麼辦？
- 如果資料已經過期，畫面還要繼續顯示嗎？

這些都是後來陸續處理的問題。

### 資料過期時該怎麼辦？

天氣跟一般靜態資訊不太一樣，因為它會隨時間改變。

如果使用者現在看到的其實是很久以前的預報，但畫面沒有任何提示，就可能誤以為那還是最新資訊。

因此，在後續開發中，我們也針對逐時預報加入資料時效判斷。

依照目前研究的實作版本，逐時預報會根據資料發布時間分成三個狀態：

| 狀態 | 判斷方式 | 顯示行為 |
|---|---|---|
| Fresh | 未滿 30 分鐘 | 正常顯示可用預報 |
| Stale | 30 分鐘至未滿 120 分鐘 | 保留可用預報，提示資料較舊 |
| Expired | 達 120 分鐘 | 不再顯示已過期的逐時預報 |

這不是在說所有天氣資料都只能使用兩個小時，而是針對這部分逐時預報所採用的資料效期規則。

另外，逐時預報的資料也不是單純拿到幾筆就直接顯示。

因為還會遇到時間排序、時區、觀測時間及資料缺值等問題。

例如 API 提供的時段可能只有時間標籤，這時就需要按照臺灣時間和有效觀測時間去挑選適合的預報，而不是直接拿資料陣列的前幾筆。

當部分資料不存在時，也不能為了湊滿畫面而自己補出假的預報。

這些邏輯雖然不像 UI 那麼明顯，但其實會直接影響使用者看到的資訊是否合理。

[相關實作：PR #582](https://github.com/ExpTechTW/DPIP/pull/582) · [PR #607](https://github.com/ExpTechTW/DPIP/pull/607)

### 自動刷新與手動更新

後來也陸續加入原生天氣刷新和互動式預報更新的機制。

原生刷新讓 Widget 可以依照設定的地點自行取得天氣資料，不一定要等使用者開啟 Flutter App。

但如果更新失敗，也需要合理處理之前已經儲存的快照，而不是因為一次網路問題就直接讓整個 Widget 失去內容。

至於逐時預報，中型與大型 Widget 在符合條件時，也能提供手動刷新入口。

不過這裡有一個限制：按下刷新按鈕，不代表 iOS 就一定會立即取得最新資料。

因為 WidgetKit 仍然會管理實際執行的時機。

所以我覺得比較重要的是把更新流程、資料效期，以及失敗時的顯示方式設計好，讓 Widget 在各種狀態下都有合理的行為。

[相關實作：PR #580](https://github.com/ExpTechTW/DPIP/pull/580) · [PR #629](https://github.com/ExpTechTW/DPIP/pull/629)

## 我最喜歡的部分，其實是 UI 設計

前面提到的資料處理跟更新邏輯，確實花了一些時間。

但如果問我整個 Widget 開發過程最喜歡什麼，我應該會選 UI 排版。

因為我很喜歡研究 Apple 的 Human Interface Guidelines，也希望自己做出來的 Widget，看起來就像 iOS 原生系統的一部分。

我不太喜歡小工具放到主畫面後，跟整個系統的風格差很多。

所以在設計時，我會特別去注意資訊間距、圖示、文字大小，以及 Small、Medium、Large 不同尺寸要怎麼安排內容。

而且每種尺寸能顯示的資訊不一樣，不能只是把同一個畫面放大或縮小而已。

### SF Symbols 與 Flutter 的圖示差異

這裡還有一個蠻有趣的地方。

DPIP 主 App 是 Flutter，介面主要使用 Material 風格；但原生 iOS Widget 則採用 SF Symbols。

所以同樣是一個天氣狀態，App 和 Widget 可能會使用不同的圖示。

這也讓我需要考慮兩個平台之間的差異。

我希望 Widget 可以符合 Apple 的原生設計習慣，但又不能讓使用者看不懂它在表示什麼天氣。

除了圖示選擇，圖示本身的高度和視覺比例也會影響排版。

尤其逐時預報通常會把好幾個時段排在一起，如果每個天氣圖示的尺寸不一致，就容易讓下方的溫度和降雨機率看起來沒有對齊。

這種問題看起來很小，但實際放在 Widget 上就會很明顯。

我自己其實蠻喜歡處理這類細節。

因為 UI 的改動可以直接看到成果，有時候只是調整一個間距或排列方式，整個畫面看起來就會順很多。

當 Widget 慢慢接近我想要的 iOS 原生風格時，真的會蠻有成就感的。

## 點擊 Widget，也要回到正確的地方

除了在主畫面查看天氣，還需要考慮使用者點擊 Widget 後的行為。

例如 Widget 現在顯示的是某個已儲存地點，使用者點擊後，應該要能在 DPIP 裡面看到對應的地點，而不是每次都回到預設位置。

這個部分也需要讓原生 iOS 與 Flutter Router 互相配合。

因為 App 有可能原本就開著，也可能完全沒有執行，甚至使用者還沒有完成初次設定。

所以不能只考慮 App 已經開啟的情況。

最後會根據 Widget 自己的地點設定來處理導向，並考慮冷啟動、暖啟動，以及地點不存在的情況。

[相關實作：PR #608](https://github.com/ExpTechTW/DPIP/pull/608)

## 測試與還沒有解決的限制

這次開發過程中，也透過 Flutter／Dart 測試、iOS 原生測試、Simulator，以及部分實體裝置檢查不同功能。

像是不同 Widget 尺寸、資料到期後的顯示、地點導向及更新流程，都有在相關 PR 中留下驗證紀錄。

但這不代表所有情況都已經完成測試。

例如不同 iOS 版本的互動式刷新、長時間背景執行後的更新狀態、實機定位及網路中斷後的恢復行為，仍有需要持續驗證的地方。

尤其 WidgetKit 的更新時機會受到 iOS 系統管理，所以模擬器或短時間測試成功，也不能直接當成所有裝置都會有相同行為的保證。

這些限制也是後續還能繼續改善的方向。

## 這次開發帶給我的經驗

這次開發 iOS 天氣 Widget，其實是我第一次比較完整地把 Flutter 與 Apple 原生技術整合在同一個功能裡面。

從一開始自己提出想法、研究 Flutter 能不能銜接 Swift，到後來真的把 Widget 做出來，再陸續補上地點設定、刷新與資料時效的處理，整個過程讓我學到蠻多東西。

不過最有成就感的，還是看到自己設計的 Widget 真正出現在 iPhone 主畫面上。

因為那不再只是程式碼，而是一個可以直接使用、也能讓其他使用者更方便取得天氣資訊的功能。

DPIP 本身是團隊共同開發的產品，這次 iOS 天氣 Widget 則是我主動提出並持續參與實作的一部分。

我希望未來還能繼續探索更多 iOS 原生功能，讓 Flutter 負責跨平台核心功能的同時，也能善用 Apple 平台本身提供的能力。

對我來說，這次最重要的收穫，就是發現跨平台 App 不代表只能使用跨平台框架提供的功能。

只要把資料流程和平台之間的責任分清楚，一樣能做出很接近原生體驗的功能。
