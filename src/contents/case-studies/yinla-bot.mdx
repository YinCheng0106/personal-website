# YINLA｜從 Replit 的 main.py，到整合臺灣資訊的 Discord Bot

**專案：** YINLA（個人開發的開源 Discord Bot）\
**主要技術：** JavaScript、Node.js、Discord.js、MongoDB、Mongoose、Cron、Next.js\
**個人參與：** 專案創立、Bot 開發、官方網站開發與後續維護

## 一切其實只是從 Discord 開始

如果要說 YINLA 是怎麼誕生的，其實一開始真的沒有想那麼多。

我大概是在 2018 年開始接觸 Discord。

當時 Discord 在遊戲社群之間越來越流行，身邊也有不少朋友開始使用。大約在 2019 年，我就建立了一個自己跟朋友使用的 Discord 伺服器。

後來因為準備 APCS，以及升學相關的事情，我開始接觸程式設計。

那個時候我還只是個剛開始學程式的新手，平常會透過 YouTube 影片和網路上的教學，慢慢摸索程式要怎麼寫。

直到後來接觸到 `discord.py`，我才發現原來 Discord 裡面的機器人也可以自己開發。

當時就覺得這個東西蠻酷的。

而且如果真的做出來，我自己的朋友也可以在伺服器裡面使用。

所以就決定試試看。

### 從 Replit 和一個 main.py 開始

最早開發 Discord Bot 的時候，我甚至還沒有使用 VS Code。

當時主要透過 Replit 這個線上開發環境寫 Python，然後一邊看教學影片、一邊慢慢把功能做出來。

而且當時的程式架構真的很簡單。

印象中，大部分的指令和處理邏輯都直接寫在同一個 `main.py` 裡面。

沒有什麼完整的模組化，也沒有特別成熟的架構規劃，就是想到什麼功能，就繼續往裡面增加程式碼。

現在回頭看，當時的寫法可能很不成熟，但那也是我開始接觸實際專案開發的一段經驗。

尤其那個時候，AI 程式輔助工具還不像現在這麼普遍，遇到不會的地方，大多就是自己搜尋、看教學，再慢慢嘗試。

不過，當自己寫的功能真的能在 Discord 裡面運作，而且朋友也能實際使用的時候，還是會覺得蠻有成就感的。

### YINLA 這個名字怎麼來的？

至於 YINLA 這個名字，其實沒有什麼特別複雜的故事。

因為我的名字中間有「YIN」，所以當時就把自己開發的 Discord Bot 取名為「YINLA」。

後來即使程式語言、架構和功能陸續改變，這個名稱也一直保留下來。

## 從 Python 到 JavaScript，幾乎重新開發整隻機器人

後來我開始接觸 JavaScript 和 Discord.js，就決定把原本使用 Python 開發的機器人重新寫過。

這次並不是把原本的程式碼逐行翻譯成 JavaScript，而是幾乎把整隻機器人重新開發了一次。

因為 `discord.py` 跟 Discord.js 的使用方式不太一樣，加上程式語言本身也不同，所以整個系統架構也跟著改變。

而且我也趁這個機會，重新整理原本的程式碼。

### 從單一檔案到模組化架構

早期使用 Python 的時候，我幾乎把所有指令和功能都寫在同一個 `main.py` 裡面。

但隨著功能越來越多，我開始覺得，如果一直把所有東西放在同一個檔案裡，後續想增加功能或修改程式，就會變得不太方便。

所以在使用 JavaScript 重新開發時，我開始把整個專案模組化。

例如一個指令使用一個檔案，不同事件也分開處理，再依照用途建立不同的資料夾。

像是 `commands` 負責指令、`events` 負責事件，而 `handlers` 則負責載入和分派不同的功能。另外，也會把部分共用工具獨立出來。

這樣之後想增加新指令時，就不需要一直修改同一個巨大的程式檔案。

如果某個功能發生問題，也比較容易找到對應的檔案。

現在回頭看，從最早只有一個 `main.py`，到後來開始整理指令、事件和處理邏輯，其實也是我慢慢學習怎麼組織程式碼的一個過程。

當然，現在的架構並不是一開始就全部設計好的，而是隨著功能增加、接觸更多技術，才逐漸演變成現在這個樣子。

這次重寫不只是讓我接觸另一種程式語言，也讓我開始理解，程式除了要能正常執行之外，還需要考慮未來要怎麼繼續開發和維護。

## 為什麼後來會加入這麼多臺灣資訊功能？

其實原因很簡單，就是因為我們當時真的很常待在 Discord 上面。

既然平常聊天、玩遊戲或跟朋友交流都會使用 Discord，我就開始想，如果一些平常會用到的資訊，也能直接在 Discord 裡面查詢，是不是就會方便很多？

所以後來就陸續開始嘗試整合更多功能。

像是天氣、地震報告、地震速報、交通資訊，以及中華職棒的賽事資料。

Discord 本身提供不少互動介面，可以透過 Slash Commands、按鈕、選單等方式讓使用者取得資訊。

YINLA 則負責向不同的外部資料來源取得內容，再整理成適合在 Discord 裡面顯示的訊息。

這些功能不是一開始就全部規劃好的。

比較像是我在開發過程中，想到什麼可能有用的功能，或是接觸到什麼新的技術，就會試著把它加入機器人。

後來也開始加入一些 AI 相關功能，例如協助整理天氣警報的摘要。

就這樣，YINLA 從原本自己和朋友使用的小工具，慢慢變成整合多種資訊的 Discord Bot。

## 不只是查詢，也要處理自動通知

除了使用者主動輸入指令，YINLA 也有一些需要定期檢查資料的功能。

例如天氣警特報、地震報告，以及中油油價更新通知。

這類功能跟一般查詢指令不太一樣。

查詢指令通常是使用者發出請求後，系統再取得資料並回覆。

但自動通知需要在背景定期執行，檢查有沒有新的資料，再依照各個 Discord 伺服器設定的頻道發送訊息。

因此，除了串接外部資料之外，還需要處理排程、伺服器設定，以及避免重複發送的問題。

目前 YINLA 使用 Cron 執行部分排程工作，並透過 MongoDB 保存相關的伺服器設定與部分通知狀態。

不同類型的通知，也會有不同的方式判斷資料是否更新。

例如天氣警特報可以比較警報內容與時間，油價則需要比較資料的更新日期。

不過，這些去重機制仍然依賴程式實際保存的狀態，不能直接視為任何情境下都不會漏送或重送的保證。

## 為什麼中油油價通知會一直重複發送？

在維護 YINLA 的過程中，我自己也發現過一些比較特別的問題。

其中一個就是中油油價的自動推播。

原本這個功能的設計，是定期檢查中油的油價資訊，如果發現有更新，就把最新資訊推送到有訂閱的 Discord 伺服器。

但有一次我發現，明明已經發送過的油價資訊，卻還是會一直重複推播。

當時我就在想，為什麼系統明明有做重複判斷，卻還是會發生這種問題？

所以我就開始往回追查，檢查資料怎麼取得、怎麼判斷，以及最後怎麼儲存。

後來才發現，問題出在油價更新時間的欄位處理上。

因為資料流程中有幾個看起來很相似的時間欄位，當初在開發時沒有把讀取與寫入的對應方式整理一致。

結果就造成程式在判斷資料有沒有更新時，讀到的內容跟原本儲存的內容對不起來。

也因為這樣，系統才有可能把已經處理過的油價資訊再次當成新資料發送。

### 不只是修掉 Bug，也重新整理欄位命名

找到原因之後，我就把相關欄位的命名與讀寫邏輯重新整理，讓油價推播流程使用一致的資料欄位。

這樣不只是為了解決重複推播，也希望未來回來維護這段程式時，可以更清楚知道每個欄位代表什麼。

因為有時候程式出問題，不一定是什麼很複雜的演算法錯誤。

也有可能只是兩個看起來差不多的變數，在不同地方使用了不一致的名稱或資料結構，就讓整個功能產生非預期的結果。

這次經驗也讓我更加重視資料欄位的命名與一致性。

尤其像這種需要定期執行、並保存上次處理狀態的功能，如果資料讀寫沒有處理好，就可能不斷重複執行同樣的工作。

## 為什麼更換中華職棒的資料來源？

YINLA 原本就有提供中華職棒的相關資訊，讓使用者可以直接在 Discord 裡面查看比賽狀況。

不過，當時我發現中華職棒原本的官方網站，在部分賽事資料的更新速度上比較慢。

後來中華職棒推出了新的數據網站 `stats.cpbl.com.tw`，我就開始研究能不能改用這個網站的資料。

主要是因為新網站有更詳細的比賽資訊，而且依照我當時的觀察，賽事資料的更新也比較即時。

另外，新網站的資料結構相對清楚，對於需要將賽事資訊整理成 Discord 訊息的應用來說，也比較方便取得需要的內容。

所以我就決定調整 YINLA 的 CPBL 資料來源。

### 重新整理資料取得方式

YINLA 的 CPBL 功能主要仍是透過爬取與解析網站資料的方式取得資訊，而不是使用一個保證長期相容的公開 API。

這次改用新網站時，需要重新研究它的資料結構與回應方式。

後來就透過 `stats.cpbl.com.tw` 使用的網站資料介面，重新整理比分、戰績與比賽詳細資訊的取得流程。

同時也建立共用的請求處理邏輯，包含逾時、重新導向、重試，以及暫存等機制，讓不同的 CPBL 指令可以共用。

這次調整主要是希望讓使用者在 Discord 裡面查詢棒球資訊時，可以取得更完整、更新速度也更符合需求的資料。

不過，因為這些資料仍然依賴外部網站的結構與回應方式，未來如果網站調整，YINLA 也可能需要跟著修改。

這也是整合外部資料來源時，需要持續面對的維護問題。

## YINLA-TEAM 其實是為了管理專案而建立的

雖然 YINLA 的 GitHub Repository 是放在 `YINLA-TEAM` 這個 Organization 底下，但其實這個組織也是我自己創立的。

當初會另外建立 GitHub Organization，主要就是因為 YINLA 這個專案。

我希望把機器人的原始碼，以及後來開發的官方網站放在同一個組織下管理，所以才有了 YINLA-TEAM。

目前 YINLA Bot 的主要程式開發、架構整理，以及官方網站，也都是由我自己負責。

雖然專案是開源的，但目前沒有其他固定的程式協作者。

所以 YINLA-TEAM 並不是一個有很多工程師共同開發的團隊，而是我用來整理與管理 YINLA 相關專案的 GitHub 組織。

### 為什麼沒有特別宣傳？

其實我沒有很刻意地宣傳 YINLA。

最初只是覺得自己寫 Discord Bot 很酷，而且朋友也能使用，所以才一直開發下去。

後來雖然也有其他人幫忙分享，讓更多 Discord 伺服器開始使用，但我並沒有特別把增加使用量當成主要目標。

因為我也會考慮到，如果使用規模真的變得很大，後續需要處理的問題、維護責任和時間成本也會增加。

尤其 YINLA 主要是我自己開發和維護，而我平常也有其他專案和事情需要處理。

因此，我不太想為了追求更多使用者，就讓自己承擔超過目前能負荷的維護工作。

而且現在中文 Discord Bot 社群也已經有不少做得很不錯的作品。

我覺得不一定每個專案都需要刻意跟別人競爭，或是追求成為使用者最多的機器人。

對我來說，能讓需要這些功能的人使用，而且自己還能負擔後續維護，就已經有它的價值了。

## 從持續增加功能，到現在以維護為主

YINLA 的開發方式，跟最早已經有很大的不同。

以前比較像是想到什麼，就會想辦法把功能寫出來。

現在則因為還有其他專案、課業和生活上的事情需要處理，所以已經比較少持續增加大型新功能。

目前主要就是維持既有功能，遇到外部 API 改變、套件更新或其他問題時，再回來處理。

例如後續也做過 Discord.js、Mongoose 和 Cron 的相依升級，調整部分舊版 API 的使用方式，以及修正一些通知功能。

不過，YINLA 並不是一個已經完全不需要維護的系統。

它依賴許多外部資料來源，像是天氣、地震、棒球與交通資訊，只要資料來源調整格式，程式就可能需要重新適配。

另外，現有公開 Repository 的自動化測試也還不完整，因此不能把程式能執行，直接等同於所有功能都已通過完整驗證。

這些都是未來如果要持續維護，仍然需要面對的事情。

## YINLA 對我的意義

如果要說 YINLA 帶給我最大的收穫，我覺得它其實不只是學會怎麼開發一隻 Discord Bot。

從最早使用 Replit 和 Python，在同一個 `main.py` 裡面寫程式，到後來重新使用 JavaScript 開發，開始把指令、事件和處理邏輯模組化，這本身就是一段蠻完整的學習過程。

後來隨著功能越來越多，我也開始接觸外部 API、資料庫、排程通知、錯誤處理，以及長期維護需要考慮的事情。

而且因為 YINLA 是自己創立的專案，所以很多問題也需要自己去研究和處理。

像是中油油價通知重複推播，或是中華職棒資料來源的遷移，都是在實際開發與維護過程中遇到的事情。

對我來說，這些經驗跟單純完成一個課堂作業不太一樣。

因為專案不會在功能寫完的那一天就結束。

只要還有人使用，就可能需要面對新的問題。

雖然現在我已經不像以前那樣一直幫 YINLA 增加功能，但這個專案仍然是我從最早開始接觸程式設計，一路學習到現在的一個重要紀錄。

它不一定是我現在技術最先進的作品，但確實是陪著我走過不同開發階段的一個專案。
